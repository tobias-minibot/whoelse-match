# Multi-intent dispatch (the intent bus)

WhoElse is a **composition engine**, not 451 vertical apps.

Humans speak naturally. Agents speak WhoElse. Externally it is still just **Who else?**

One NL/voice request can carry **multiple** atomic intents + params + constraints + relationships + actions. The product is that one request can recruit many AIs, humans, and services on **one core**.

```
NL  →  compound IR  →  intent graph  →  parallel whoelse.find  →  reconcile  →  one plan  →  confirm
```

There is no `date.find`, `tennis.find`, `apartment.find`, or `school.find`. Nodes are subrequests. The matcher is always `whoelse.find`.

### Kinds (what composes)

| Kind | Examples | Typical edge |
| --- | --- | --- |
| **need** | DATE, JOB, SCHOOL, REMOTE WORK | intersect / constrains |
| **activity** | TENNIS, YOGA, HIKING | intersect with DATE |
| **entity** | APARTMENT, HOTEL, FLIGHT | constrains / sequence |
| **service** | DOCTOR, PLUMBER, LAWYER | parallel, then a plan |
| **atomic** | leftover MISC | compose if spoken |

Entities vs activities vs needs vs services are metadata for the graph, not separate engines.

## Compound IR

Native shape in `@whoelse/core` (`parseCompound` / `whoelse.compile`). A single intent is a **degenerate compound**.

```
Request
  intents[]     vocab labels (DATE, TENNIS, …)
  entities      seeker / target kinds (human, …)
  hard          CONSTRAINT ops
  soft          location, time, price, trust, relation
  exclusions
  relations[]   parallel | depends | constrains | intersect | fallback | sequence
  actions[]     discover, coordinate, confirm, connect, …
  permissions   find does not persist; confirm is a later ACT
```

Canonical:

> “Find me someone nearby I might like who wants to play tennis tonight.”

```
DATE ∩ TENNIS
  WHERE = nearby
  WHEN  = tonight
  RELATION = romantic
  ENTITY = human
  ACTION = discover + coordinate
```

Not a dating category. Not a tennis app.

Spoken twin (same IR):

> “I want to play tennis with someone I might like romantically tonight, somewhere nearby.”

Second domain (same bus):

> “Find me an apartment near a good school in DC.” → APARTMENT constrained by SCHOOL.

Also: FLIGHT → HOTEL (sequence), JOB constrained by REMOTE WORK.

## Graph + dispatch

`buildDispatchPlan(ir)` turns intents into nodes (each node = one `whoelse.find` with slots) and edges into waves.

- **intersect** (DATE ∩ TENNIS): both nodes ready; one concurrent wave; reconcile by coverage then score.
- **constrains** (SCHOOL → APARTMENT): both may run in parallel; apartments kept if they share place with a school hit.
- **sequence** (FLIGHT → HOTEL): hotel waits on flight when the edge is `depends`/`sequence`; result is one ordered plan.
- **fallback**: B only if A is empty.
- **parallel**: independent finds, still one ranked list (not concat).

Playground honesty from #20 is preserved: pick **one** pool (live vs labeled playground) from the original sentence, then every node runs on that engine. Never mix the two lists.

Reconcile returns **one** `WhoElseResult` plus `composedFrom` and `composition.explanation`. Intersection is not “here are dates, and also here are tennis players.”

## Surfaces

| Surface | Behavior |
| --- | --- |
| Human Who else? box | Typeahead against the shared vocab (label, aliases, questions, categories). Pick inserts/refines the sentence and a chip — not a schema UI. Compound NL → compile+dispatch when there is no exemplar. Quiet line: `composed from DATE + TENNIS`. Recursive **Who else like this?** stays atomic find. |
| `/universe` (`/intents`) | Full-text filter + `?q=` deep link. Coverage A–E is still the index; search is how you find a row. |
| `whoelse.compile` | Compound IR always. `find: true` dispatches when `intents.length > 1`. Also returns `vocabHits` for discovery. |
| `whoelse.intents` | Vocab search for agents. Same catalog as the box / universe. |
| `whoelse.dispatch` | Compile → plan → parallel find → reconciled result. |
| `whoelse.find` | **Atomic.** Agents who already know a single intent skip the graph. |

HTTP twins: `POST /api/compile`, `POST /api/dispatch`, `POST /api/whoelse`.

## Production demo (e2e)

Production starts empty. Empty find is real. The tennis-date people live in the **labeled playground** seed, so a cold visitor still feels the question (honesty banner). Live matches, when they exist, come first.

1. Open https://whoelse-dating.vercel.app
2. Spark **Tennis tonight** or paste: `Find me someone nearby I might like who wants to play tennis tonight.`
3. Confirm the quiet line `composed from DATE + TENNIS · intersect`.
4. Cards are one ranked list (Elise / Marco / Jun in the playground). Not two columns of apps.
5. Open **How WhoElse heard this** — graph shows DATE + TENNIS, nearby, tonight.
6. **Who else like this?** on a card stays recursive find on the same core.
7. Same infra, other domain: `Find me an apartment near a good school in DC.` → APARTMENT + SCHOOL, constrain, Adams Morgan listing near the demo school.
8. Agent path (no key needed for compile/dispatch):

```bash
curl -sS -X POST https://whoelse-dating.vercel.app/api/compile \
  -H 'Content-Type: application/json' \
  -d '{"text":"Find me someone nearby I might like who wants to play tennis tonight.","find":true,"limit":5}'

curl -sS -X POST https://whoelse-dating.vercel.app/api/dispatch \
  -H 'Content-Type: application/json' \
  -d '{"text":"Find me an apartment near a good school in DC.","limit":5}'
```

MCP: `whoelse.compile` / `whoelse.dispatch`. Never `date.find`.

Confirm (propose match / ACT) is the existing closed loop. Dispatch does not write MATCH.
